# MLflow Research Project

Build research projects with pixi environments, Hydra-configured experiments,
MLflow runs and artifacts as the evidence record, and Folio reports as the
reviewed account of the method and findings. This is a standalone alternative to
the Cairn-based `research-project` skill; do not install Cairn or inherit its
run callbacks, store, publishing commands, or server requirements.

## Workflow

Before scaffolding or changing tracking, read
[references/project-setup.md](references/project-setup.md). Before authoring or
building a report, read [references/reports.md](references/reports.md). For
method development and report review, read
[references/research.md](references/research.md). Before writing or revising
Abstract, Background, or Methods, read
[references/writing-methods.md](references/writing-methods.md) and, once per
project, [references/example-methods.md](references/example-methods.md).
Review every changed direction report against
[references/review.md](references/review.md).

1. Inspect the existing project and preserve its scientific and framework
   choices. For a new project, establish pixi and commit its lock file; use
   Hydra `_target_` configs and `hydra.utils.instantiate` to construct the
   experiment. Keep experiment logic outside the entry point.
2. Start one MLflow run per independently executed trial. Record the resolved
   config, overrides, seed, source revision, environment and input identities,
   metrics, diagnostics, and report-ready files. Use exact run IDs in evidence
   references; a display name is not an identity.
3. Develop the method with the user: resolve consequential ambiguities, make
   intermediate behavior inspectable, and establish feasibility against faithful
   baselines before tuning or scaling. Identify smoke tests and debugging
   proxies as such.
4. Log report evidence in an artifact directory such as `evaluation/` containing
   JSON/CSV and figures. Folio reads this directory through
   `runs:/<run-id>/evaluation`; it does not query MLflow's metric database.
5. Maintain one coherent, paper-like report per research direction at
   `reports/<slug>/report.md`. Results are computed from declared inputs, never
   manually transcribed. Pin finished runs, build, inspect the rendered report
   and changed figures, and review claims against the evidence.
6. Hand off what changed or was learned, validation and limitations, exact run
   IDs/artifact URIs, reproduction commands, and the built report paths or URLs.
   Export Folio's standalone HTML unchanged when a single file is needed.

## Developing a method

**Establish shared understanding.** Ask focused questions about ambiguities in
purpose, inputs, outputs, operations, state, update rules, objectives,
invariants, assumptions, intended advantages, and failure cases. Restate the
interpretation with equations, pseudocode, diagrams, or simple examples and ask
the user to confirm it. Record confirmed choices in config, code, and the
report's Methods. Reopen the discussion when implementation exposes a
consequential ambiguity.

**Make behavior inspectable.** Create simple examples that expose important
mechanisms. Visualize inputs, intermediate states, transformations, outputs,
loss terms, update directions, small optimization trajectories, baseline
comparisons, ablations, and representative failure cases as appropriate:
enough complementary views for the user to verify the implementation, not
decorative figures. Prefer image grids for related inputs, references,
predictions, residuals, masks, or steps.

Treat every repeated dataset, seed, model, or method comparison as one
visualization family with a declared visual grammar: keep chart type, model
colors, axis orientation, limits and scales, ordering, normalization,
aggregation, and panel layout stable, generated by one plotting function.
Figures from separate runs need cross-run limits and ordering passed explicitly
from a shared config, not derived from each run's own data. Change a
visualization only when the analytical question changes, say why in the report,
and never switch chart types because one representation flatters the preferred
method.

**Stay inside the framework's ecosystem.** Build the method from the
framework's own abstractions and extension points, so it composes with the
framework's tools, baselines, and other people's code, instead of a parallel
structure beside them:

- **Mitsuba / Dr.Jit:** implement a rendering method as a Mitsuba plugin (an
  integrator, BSDF, emitter, sensor, or texture, registered with
  `mi.register_*` and selected in the scene or config). Render with
  `mi.render`, differentiate with Dr.Jit's autodiff and `mi.ad` integrators,
  optimize scene parameters through `mi.traverse` and `mi.ad.Adam`, and write
  array code with `dr.*` operations and symbolic loops, not Python loops over
  samples or NumPy round trips. Integrators have two constructors (Mitsuba
  properties and a direct signature for Hydra) and scenes come from constructor
  functions: see [references/mitsuba.md](references/mitsuba.md).
- **PyTorch:** models and learned components are `nn.Module`s with their
  parameters registered, losses use `torch.nn.functional` or loss modules, data
  comes through `Dataset` and `DataLoader`, and training uses `torch.optim` and
  its schedulers. Do not keep parameters in hand-made lists or write your own
  optimizer step.
- **Any other framework:** find its equivalent (a JAX/Flax module, a
  scikit-learn estimator, a solver library's problem class) before writing one.

Leave the framework only where it cannot express the method, and say so in
Methods. A baseline reimplemented outside the framework is not a faithful
adaptation.

**Build diagnostics with Matplotlib.** Write reusable functions that take
explicit data and return a `Figure`, with units, labels, legends, and colorbars
where needed, method colors and ordering centralized in one module. Add the
figures to the MLflow run with `mlflow.log_figure(figure, "evaluation/figures/<name>.png")`
and reuse the same functions in the reports.

**Establish baselines and feasibility.** Agree with the user which baselines
test the claimed advantage. Prefer faithful adaptations of authoritative
reference implementations: read the paper, documentation, configuration,
evaluation protocol, and the complete relevant execution path; record the
reference version and material deviations. Begin with a bounded feasibility
study, with agreed checks, metrics, tolerances, and failure cases. Do not start
systematic tuning, large multiruns, or expensive scaling until the user has
seen the evidence and the method has passed this gate.

**Leave the user's machine usable.** Runs on the user's own computer use at
most half its cores unless the user asks for more: cap worker processes and
library threads (`OMP_NUM_THREADS`, `torch.set_num_threads`) in config, and size
a feasibility study to the budget the user gave. Larger work goes to a cluster.

**Perceptual blind spots.** When the user reports an effect that inspection or
metrics miss (temporal instability, localized artifacts, high-frequency
structure), preserve the original outputs, add a visualization that isolates
it, and record a quantitative measure: a standard metric when its assumptions
fit, otherwise one tested on known positive, negative, and confounding cases.
If its relation to perception stays unclear, propose a small calibration with
focused ratings or pairwise comparisons.

## Evidence and responsibilities

- **pixi** owns packages and reproducibility. Prefer PyPI for Python packages,
  conda-forge for interpreters and native tools; commit `pixi.lock`.
- **Hydra** owns scientifically meaningful config and object construction. Keep
  job folders separate for single runs and multirun trials; keep
  `hydra.job.chdir: false` so project paths retain their meaning.
- **MLflow** owns run status, parameters, metrics and artifacts. Its ordinary
  logging APIs do not automatically snapshot all source, capture all output,
  establish input lineage, or freeze artifacts. Implement and verify the
  provenance capture needed by the project; never claim Cairn's guarantees.
- **Folio** owns report execution and rendering. Its manifest hashes the input
  contents observed during a build; it does not make a mutable artifact store
  immutable or reject unfinished MLflow runs. Check run status before citing
  evidence and preserve cited files. Revisions get new runs, not overwritten
  evidence under an existing URI.

Use the cluster skills only when remote execution is needed: `slurm` with
`kuma`/`lyra`, or `hyperqueue` for the lab workstations. Retain their
scheduling, storage and efficiency guidance, but replace Cairn-specific tracking
with this skill's MLflow flow. Do not copy a Cairn finalizer or configure a
Cairn hub.


## Finishing a turn

Reports must follow the paper-like spine in `references/writing-methods.md`:
Abstract, Introduction, Background and related work, Methods, results and
discussion, Conclusion. Keep Abstract first and Conclusion last. The full
writing guidance, worked Methods example, and review rubric are retained from
the original research skill, with MLflow/Folio-specific adaptations.

The Stop hook runs `scripts/report_gate.py`. When report sources change, it
checks their structure and that the Folio build is current, then sends you
back once to review the rendered reports and Methods figures against R0–R9.
Fix failures in the sources and rebuild; never pad sections to pass an item.
After three consecutive blocks the hook permits stopping and reports what
remains open. Tell the user any unresolved review items and why.

Hooks run only in hosts that support skill Stop hooks. In other hosts, run
`python3 <skill-directory>/scripts/report_gate.py` with a JSON event containing
`cwd` on stdin, and perform the same build and review explicitly; do not claim
automatic enforcement where the host does not support it.


## Starting a project

Copy this checklist into your reply and tick it off:

```text
Project setup:
- [ ] Read references/project-setup.md and references/reports.md
- [ ] pixi.toml with MLflow, Hydra and Folio; pixi install; commit pixi.lock
- [ ] Explicit tracking URI and durable artifact storage; verify upload/download
- [ ] Hydra configs, experiments/run.py, Experiment base; one MLflow run per trial
- [ ] Config, overrides, source, environment, inputs and logs recorded as described
- [ ] Cluster files and launcher dependencies from the relevant skills when needed; no Cairn callbacks/finalizers
- [ ] .gitignore and tooling exclusions for environments, data, outputs and stores
- [ ] Git initialized and scaffold committed before experiments
- [ ] Bounded smoke run logs evaluation JSON/CSV and figures; Folio builds from its exact run URI
- [ ] Replace smoke-test content with the project's own paper-like direction report
```

## Report changes

Reports are the primary research interface. Create them at the start of the
project and keep the current method, questions, decisions, findings,
supporting and contradictory evidence, limitations and next experiments there.
Keep one flat, single-page report per research direction, not an append-only
activity log or one page per experiment. Each direction's Introduction states
the shared project target and what this direction contributes. Cross-link
related directions rather than repeating content. A proposed direction goes
in the motivating report's Conclusion until it begins.

Each report has accurate `title`, `status` and a frontmatter `summary:` of
one to three sentences (at most 400 characters), stating what it tests, the
current result/state and what is pending. Use a YAML block scalar for summaries
containing `{{ }}` values. Keep the abstract, summary, findings and conclusion
consistent after new evidence. Reviewed findings live in the report's finding
blocks, with status, input/file references, limitations and last review date;
surface contradictions and mark superseded conclusions rather than silently
rewriting the knowledge record.

Copy this checklist into your reply whenever you change a report:

```text
Report change:
- [ ] Read the reference for this step (writing-methods.md for Abstract, Background, Methods; example-methods.md once per project)
- [ ] New evidence logged by FINISHED MLflow runs; exact run IDs declared under inputs:
- [ ] Edited reports/<slug>/report.md (and assets/) only; results as {{ }} values from inputs
- [ ] Required paper-like spine present and ordered: Abstract, Introduction, Background and related work, Methods, results and discussion, Conclusion
- [ ] Methods describes the implementation, with the mechanism figures a paper would have
- [ ] pixi run report-build succeeds
- [ ] Looked at every figure I added or changed
- [ ] Re-read the whole built report and reviewed R0–R9; summary, abstract, findings and conclusion match the evidence
- [ ] Rebuilt after corrections; exported/distributed the generated output when requested
```

## Handoff

Before handing off changes to setup, evidence or reports, go through the full
[reproducibility checklist](references/checklist.md).

State what changed or was learned, what validation supports it, and what could
still limit the conclusion. Distinguish smoke tests and proxies from evidence.
Give exact commands for reproducing experiments, rebuilding and exporting
reports, the MLflow run IDs and artifact URIs the reports read, concrete report
paths/URLs and any review items left open. Say that the user can paste a page's
copy-location markers to point at a line or figure, and that reviewed findings
live in the reports' finding blocks.
